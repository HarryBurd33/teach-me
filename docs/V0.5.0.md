# Teach-me v0.5.0

This release closes two practical v0.4.0 gaps: typed graph records no longer need separate transport, and cross-file consistency review can be recorded against exact file bytes. The tools remain optional local helpers for a learning skill.

## Plan and resulting behavior

1. Preserve explicit graph, proposal, source and review files through existing pack/unpack, immutable snapshots and three-way merge. Validate types, proposal source SHA256 and exact Unicode quote spans before output.
2. Prepare a packet describing the current journey, inspect the actual content, record four review decisions with rationales, and detect drift. `needs_changes` means the review is incomplete; an all-consistent receipt remains an operator judgment.
3. Verify failure preservation, compatibility, installed behavior, public CI and immutable downloads before release.

The fixed optional names are `knowledge-graph.json`, `knowledge-proposal.json`, `knowledge-source.txt` and `journey-review.json`. Arbitrary files are excluded. Legacy-only archives still use format v1; typed archives use v2. New helpers read both versions; older helpers cannot read v2. Progress schema v1 is unchanged. Draft proposals are never applied automatically, and unresolved draft references are not mastery evidence.

The review checks cover goal/stage/next action, evidence scope, sources/claims and merge consistency. The packet includes the exact content manifest. Each decision must say `consistent` or `needs_changes` with a concrete rationale; all four are required. Verification distinguishes current/all-consistent, current/needs-changes and stale/invalid records. Receipts cannot authenticate the reviewer or establish truth, competence or authority. File-byte changes, including optional-file addition/removal, invalidate freshness. Historical stale receipts remain transportable.

See [archive rules](../teach-me/references/transfer.md), [snapshots and merge](../teach-me/references/journey-versions.md), and [consistency review](../teach-me/references/coherence-review.md).

## Validation

All **178 tests passed** against both the integrated candidate and global installation: 125 prior regressions, 13 typed-asset cases, 25 consistency-review cases, 14 frozen independent cases and one independent post-inspection size-bound supplement. Native `skills/list` with forceReload found the enabled user-scope skill from two directories without starting a model turn. All 34 installed files match the reviewed candidate. The old v0.4.0 installation is retained locally for rollback.

Independent review verified the frozen checks and found no open actionable defects. It caught a stale README claim, which was corrected. Parent inspection also added explicit output-size enforcement, propagated draft warnings and aligned stale-receipt diagnostics with packet verification. A valid near-limit decisions file that expands beyond 2 MiB is rejected before publication.

The baseline comparison directly reproduced v0.4.0 omitting graph/proposal/source files. Four literal simulated model responses met their frozen checks with zero critical violations; the reviewer generated and graded them in a shared inherited, nonblind context, with effective model/effort unknown. This is a narrow workflow check, not independent proof of teaching quality. A test-authoring NameError was corrected and retained in the component report. An initial parent test wrapper ended without a report; the completed captured run is the result counted here.

[Versioned evidence](../validation/v0.5.0/combined-tests.json), [independent review](../validation/v0.5.0/review/static-review.json) and [baseline comparison](../validation/v0.5.0/review/baseline-comparison.json) preserve the methods and limitations. Public CI and immutable-source download verification are final release gates recorded with the release. Software checks and simulated model examples do not establish real learning gains. Historical failures and partial checks remain in the earlier release reports.

## Remaining limitations and next steps

| Area | Remaining limit | Evidence needed for a further improvement |
| --- | --- | --- |
| Meaning and learning | Tools validate structure, quotes, hashes and recorded judgments. They cannot determine whether an inference is sound or a learner has mastered a topic. | Domain-qualified content review and consenting real-learner baseline, retention and transfer observations; report assistance and confounds. |
| Model behavior | Simulated examples inspect limited workflows. They do not guarantee instruction selection or consistent teaching across models. | More independent model/effort contexts and actual learner trials with frozen cases and honest failures. |
| Native compatibility | The native-v1 adapter implements a documented subset; no full legacy compatibility, semantic search, upstream writeback or interactive graph editor. | Versioned synthetic fixtures plus permission/rights review before adding each format or UI. |
| Storage | Eleven named records, finite file/store bounds, cooperative local locks and manual merge. No distributed/background sync, live multi-file transaction, encryption, pruning or arbitrary attachment management. | Design a migration/conflict/privacy contract and fault tests before any expanded storage service. |
| Review history | A receipt records a claimed reviewer role and judgments; it is not signed. Replacement keeps one previous receipt; snapshots retain chosen history. | Explicit identity/signature requirements or an append-only history contract if users need audit assurance. |
| Execution | The local runner inherits host permissions; it is not an OS sandbox or quota monitor. Detached descendants and Windows process-tree behavior have limits. | Platform-specific isolation and child-lifecycle tests in a verified host; never infer isolation from exit zero. |
| Host integrations | Media inspection, dictation, reminders and providers depend on actual host tools and authorization. No background service or paid client is installed. | Test the selected host and obtain applicable authorization and spending bounds before integration. |
| Failure scope | Atomic create-new publication requires local hard links. Hard termination can leave staging files or locks; hostile filesystem races and universal power-loss durability are outside the guarantee. | Filesystem/platform fault trials and explicit recovery procedures; preserve uncertain artifacts instead of stealing locks. |

No immediate migration is required for existing legacy journeys. Keep the whole installed skill folder together. Preserve customized copies before updating, inspect actual combined content after a merge and re-review after changes.
