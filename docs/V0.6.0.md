# Teach-me v0.6.0

This release adds optional immutable review history and recoverable snapshot maintenance. It addresses two local storage limits from v0.5.0 while preserving teaching behavior, progress schema v1 and the eleven-name journey transfer contract.

## Plan and behavior

1. Keep exact consistency-review receipts in a separate bounded hash-linked store. Validate each receipt against the current journey before appending with an expected tip; preserve unresolved `needs_changes` decisions as such.
2. Plan retirement of explicit old snapshot hashes. Protect HEAD and its previous revision, bind the plan to the whole current store, copy and verify a complete archive, then remove only selected source revisions.
3. Verify failures and compatibility, install the accepted candidate with rollback, and validate CI and immutable source/release downloads.

[Review history](../teach-me/references/review-history.md) supports append, status and exact-byte extraction. Entries contain `version`, `journey_id`, `sequence`, `previous`, `receipt_sha256` and `receipt_base64`; sequence and previous hashes bind their order. The filename binds canonical entry bytes. Receipts remain operator judgments. A hash chain detects corruption against its current contents; it cannot authenticate the reviewer, prevent an adversary rewriting the whole store, certify truth or establish mastery. Historical receipts can become stale after journey edits. Appending requires a currently matching receipt; stale original receipts cannot be backfilled through this command and must be preserved separately.

[Snapshot maintenance](../teach-me/references/snapshot-maintenance.md) provides an inspectable plan and explicit apply. It refuses stale plans, protected or unknown revisions, foreign outputs and uncertain staging. No automatic age policy, digest chronology, pruning service, lock theft or learner resume is introduced. Before a complete verified archive exists, it deletes no source revision. If removal later fails, the archive and protected revisions remain; inspect both locations and make a fresh plan instead of replaying blindly.

Both stores are explicit local directories outside the journey. They are not silently included in journey ZIPs and need separately reviewed private transport. The archive can restore a retired revision through the existing transfer helper into a fresh workspace. Copying a history/archive store does not transfer permissions or authenticated identity.

## Validation

All **238 tests passed** against both the integrated candidate and global installation: 178 unchanged regressions, 26 history cases, 21 maintenance cases, eight frozen independent integration methods, three independent fault cases and two post-inspection actual-limit tests. The actual-limit tests accepted exactly 64 MiB of recognized history staging bytes and rejected one extra byte, and rejected more than 64 MiB of selected valid snapshot ZIPs. These later parent checks close the actual-size gaps noted in the earlier component reports.

Independent review found no blocking issue and independently reproduced the store fingerprint. Copy and stage-verification faults invoked no selected-source removals. A second-removal fault retained complete verified archives, restored both selected ZIPs, preserved HEAD/previous bytes and refused old-plan replay. Existing and racing foreign archive directories remain untouched.

Four literal baseline/candidate workflow comparisons met the candidate checks with zero critical violations. A fresh delegated evaluator generated and graded both arms in a shared, nonblind comparison context; effective model/effort were unknown. The baseline honestly identified missing native operations. These examples establish scoped workflow behavior, not causal learning gains.

The history component initially had a macOS temporary-path fixture setup error; resolving the fixture root corrected it without a production change. Original failure records remain. The integrated CI adapters change paths and wrap retained fault functions; current baseline fixture helpers were verified byte-identical before adoption.

All **38 files** match the reviewed candidate and installed skill. Native forceReload user-scope discovery succeeded from two directories with zero model turns. v0.5.0 is preserved locally for rollback. See [test results](../validation/v0.6.0/combined-tests.json), [independent review](../validation/v0.6.0/review/REPORT.md), [porting record](../validation/v0.6.0/test-porting.json) and [actual-limit checks](../validation/v0.6.0/actual-limits.txt). The [public evidence hashes](../validation/v0.6.0/review/public-evidence-hashes.json) verify the redacted logs; the original evaluator hash manifest is explicitly labeled as pre-redaction. Frozen case and criteria hashes are unchanged. Public CI and immutable source/release download checks are recorded with the final tagged release. These checks do not establish real learning gains. Historical failures and partials remain in prior reports.

## Remaining limitations and next steps

| Area | Still needed | Next evidence or implementation |
| --- | --- | --- |
| Learning and meaning | Domain judgment, source evaluation and real learner outcomes | Run consenting baseline, independent application, retention and transfer checks; record assistance and confounds. |
| Model reliability | Broader independent model/effort trials and native selection behavior | Run frozen workflows in separate qualified contexts; retain failures and distinguish explicit loading from automatic selection. |
| Trust and history | Authenticated reviewers and an external trust anchor | Define identity/signature/key-management requirements before implementing signed records. Hashes alone do not authenticate or prevent whole-store replacement. |
| Storage | Distributed/background synchronization, encryption and arbitrary attachments | Define privacy, conflict, migration and recovery contracts before adding a service. History and archive stores need explicit transport and have finite bounds. |
| Maintenance recovery | Automatic reconciliation of interrupted removal or incomplete archive publication | Keep the conservative manual inspection/fresh-plan workflow until platform fault tests justify a recovery protocol. No automatic deletion or lock/stage cleanup. |
| Native data and map UI | More native/legacy formats, upstream writeback, semantic search and interactive editing | Add versioned synthetic fixtures and review rights/compatibility for each format or UI. |
| Execution and integrations | Stronger OS containment, detached/Windows child handling and verified media/reminder/provider access | Test the selected host and obtain applicable authorization and spending limits. The local runner inherits permissions; no background service or paid client is added. |
| Filesystem guarantees | Hostile races, unsupported hard links and universal power-loss durability | Test relevant platforms/filesystems and retain uncertain artifacts. Cooperative locks do not fence arbitrary editors or hostile processes. |

Existing journeys need no migration. Update the whole skill folder together. Older versions do not understand the new optional history/maintenance tools; the journey ZIP formats remain v1/v2 as documented in v0.5.0.
